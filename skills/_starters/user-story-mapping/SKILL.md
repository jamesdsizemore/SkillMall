# User Story Mapping

Build a shared understanding of user journeys and slice them into releasable increments. Based on Jeff Patton's User Story Mapping method, which prevents building complete features nobody uses by keeping the full narrative visible.

## When to use

- Starting a new product or major feature
- Planning a release with too many stories to prioritize in a flat backlog
- When the team disagrees on what "minimum" means in MVP
- Reconnecting a team to user value after too long in feature-factory mode

## The map structure

**Backbone (top row):** User activities — the major stages of the user's journey through your product. Written as verbs: "Browse skills", "Deploy skill", "Track usage". Left-to-right narrative.

**Tasks (second row):** User tasks within each activity — what a user does within that activity. More granular. "Filter by category", "Sort by rating", "Preview SKILL.md".

**Stories (below tasks):** The actual user stories. Each column of stories under a task is a vertical slice.

## Walking skeleton

The walking skeleton is the minimum set of stories that completes the entire journey end-to-end. Not all features — just enough to go from start to finish. This is your first release candidate.

## Release slicing

Draw horizontal lines across the map to define releases. Stories above the first line are Release 1, between first and second are Release 2, etc.

**The key insight:** Each release slice is a horizontal cut across the entire backbone, delivering end-to-end value — not a complete implementation of one feature.

## Running a story mapping workshop

Time: 2-4 hours. Participants: product, design, engineering (limit to 8 people). Materials: sticky notes or a virtual board.

1. Walk through the user journey out loud — no stories yet
2. Write backbone activities on top row
3. Break each activity into tasks
4. Write stories beneath each task
5. Draw the walking skeleton line
6. Draw subsequent release lines
